## 3. 网络连通性（关键）

Java 和 Python 需要访问虚拟机里的 MySQL 与 Milvus，因此必须确认：

| 检查项 | 方法 | 期望 |
|---|---|---|
| 宿主机能否 ping 通虚拟机 | `ping <VM_IP>` | 通 |
| MySQL 可达 | `Test-NetConnection <VM_IP> -Port 3306` | TcpTestSucceeded: True |
| Milvus 可达 | `Test-NetConnection <VM_IP> -Port 19530` | TcpTestSucceeded: True |
| 防火墙 | 虚拟机内 `systemctl status firewalld` | 端口已放行 |

**注意**：容器端口映射是 `0.0.0.0:19530->19530`，所以只要虚拟机能被访问到，Milvus 就能连。
如果虚拟机是 **NAT 模式**，宿主机无法直接访问虚拟机 IP，需要改桥接模式，或在 VMware/VirtualBox 上配置端口转发（把宿主机 19530/3306 转发到虚拟机）。

**实测结论（已在开发机验证）**：VM 的 IP 是 **192.168.1.100**，网络模式是 VMware **VMnet8（NAT）**，
宿主机在 VMnet8 上持有 `192.168.1.1`，因此**宿主机可以直接访问虚拟机，不需要改桥接也不需要端口转发**。
10 个端口全部探测为 OPEN，Milvus 的 `GET :9091/healthz` 返回 **HTTP 200 / OK**。
NAT 模式的限制只在「局域网内其他物理机访问 VM」时才出现 —— 将来做手机端访问才需要处理。

### 4.3 🔴 最容易被忽略的一步：`LLM_MOCK` 开关

`.env` 里有一个 **`LLM_MOCK`**，它决定整个 AI 能力是走真实模型还是走本地 Mock：

| 值 | 行为 | 什么时候用 |
|---|---|---|
| `true` | 用 `app/services/mock_llm.py` 里的规则法。真的从材料/简历里抽句子套模板，**不花一分钱**，链路能完整跑通 | 还没有 Key、只想验证流程；或调代码时不想烧 token |
| `false` | 走 `bb_ai_provider` 里启用的真实厂商（当前是 DeepSeek Chat） | 正常使用 |

**这个开关的症状特别好认**：AI 能跑通、也不报错，但**输出很粗浅**——

- 出题永远是「下列说法正确的是」那种同义改写；
- 模拟面试永远问「你简历里写了 X，说说你在项目里怎么用它」，**不会顺着你的回答追问**；
- 评分每轮都差不多，因为它是按「回答长度 + 关键词命中率」算的。

> 所以：觉得「AI 好像不太聪明」时，**先看一眼 `LLM_MOCK`**，
> 再看健康检查里显示的模型名（Mock 模式下会显示成 `mock-llm`）。
>
> 切到真实模型只要两步：
> ```powershell
> # 1. 改 beibei-agent/.env
> LLM_MOCK=false
> # 2. 重启 beibei-agent（Prompt 模板与厂商配置都有进程内缓存，不重启不生效）
> ```
> **不需要**在 `.env` 里再填一遍 `DEEPSEEK_API_KEY` ——
> 只要「设置 → AI 配置」里那个厂商是 `enabled=1` 且 `is_active=1`，就会自动用它。

> **API Key 的真实归属**：运行时的 Key 存在 MySQL 的 `bb_ai_provider.api_key_enc`（AES 加密），
> `.env` 里的 Key 只作为首次启动时的兜底初始值。前端改了配置以数据库为准。

## 5. Milvus 2.5.23 使用要点

### 5.1 Python SDK 版本必须对齐

```text
Milvus 2.5.23  →  pymilvus 2.5.x      ✅ 用这个
                   pymilvus 3.x        ❌ 面向 Milvus 3.0，不要装
```

`requirements.txt` 里写 `pymilvus>=2.5.4,<2.6`。

### 5.2 Collection：稠密 + 稀疏双向量，一次搞定混合检索

Milvus 2.5 内置 BM25 全文检索，所以**不需要 ES，也不需要 MySQL 的 ngram 全文索引**。
一个 collection 同时容纳：

| 字段 | 类型 | 说明 |
|---|---|---|
| `pk` | Int64, 非自增 | 等于 `bb_doc_chunk.milvus_pk` |
| `vector` | FloatVector(dim=1024) | BGE-M3 稠密向量 |
| `sparse` | SparseFloatVector | 由 `text` 字段经 BM25 Function 自动生成 |
| `text` | VARCHAR(8192), enable_analyzer=True | 分块原文，供 BM25 分词 |
| `doc_id` / `kb_id` / `chunk_index` | Int64 | 标量过滤 |
| `tag_ids` | Array&lt;Int64&gt; | 按知识点过滤 |

索引：`vector` 用 HNSW(COSINE)，`sparse` 用 SPARSE_INVERTED_INDEX(BM25)。
检索：`hybrid_search` + `RRF` 重排，稠密与 BM25 各取 top 20，融合取 top 8 送进 prompt。

> ⚠️ 首次启动 `beibei-agent` 时会有一个**探针脚本**先验证 BM25 Function 在 2.5.23 上正常可用；
> 若创建失败则自动降级为「纯稠密检索 + MySQL ngram 兜底」，不会阻塞主流程。

### 5.3 数据一致性

MySQL 的 `bb_doc_chunk` 是主数据，Milvus 是索引副本。
删除文档时先删向量再删分块；提供 `/api/sys/consistency-check` 做双向校验与修复。

### 5.4 🔴 Milvus 的开机自启动（已配置并实测）

**症状**：虚拟机重启后，MySQL / Redis / Nacos 都自己起来了，**只有 Milvus 没起来**，
宿主机连 `192.168.1.100:19530` 不通，整个应用报「向量库不可达」。

**根因**（不要被 `docker.service` 的 enabled 迷惑）：
- `docker.service` 确实是 `enabled`，所以 Docker 守护进程会自启；
- VM 里绝大多数容器（mysql / redis / nacos / mq / es / gogs …）都在各自的
  `docker run` 或 compose 里带了 `restart: always`，所以跟着起来了；
- 而 **Milvus 的 compose 文件里三个服务都没有 `restart` 策略** ——
  于是 `docker ps -a` 里它们全是 `Exited (255)`。

**修法（两层保险，都已落地）**

1. **compose 加 restart 策略**：`/usr/local/src/docker-milvus/docker-compose.yml`
   的 `etcd` / `minio` / `standalone` 三个服务各加一行 `restart: always`。
   这是兜底层——即使不走 systemd，Docker 守护进程重启也会把它们拉起来。

2. **systemd 单元 `/etc/systemd/system/milvus.service`**（主力）：
   保证 `etcd → minio → standalone` 的启动顺序（`docker-compose up` 会读 `depends_on`，
   而单靠 `restart: always` 是三个容器同时被拉起、没有顺序），
   并提供 `systemctl start|stop|status milvus` 统一入口。

```ini
[Unit]
Description=Milvus standalone (docker-compose @ /usr/local/src/docker-milvus)
Requires=docker.service
After=docker.service network-online.target
Wants=network-online.target

[Service]
Type=oneshot
RemainAfterExit=yes
WorkingDirectory=/usr/local/src/docker-milvus   # 必须 cd：compose v1 按工作目录找文件，
ExecStart=/usr/local/bin/docker-compose up -d   # 且 volumes 的相对路径也依赖它
ExecStop=/usr/local/bin/docker-compose stop
TimeoutStartSec=0

[Install]
WantedBy=multi-user.target
```

```bash
systemctl daemon-reload
systemctl enable milvus.service     # → multi-user.target.wants/milvus.service
systemctl start  milvus.service
```

**一键脚本**（幂等，自带备份与回滚）：

```powershell
# 配置自启（改 compose + 写 unit + enable + start）
python scripts/vm_ssh.py -f scripts/setup_milvus_autostart.sh
# 验证 unit 真的管得住这套容器（stop → 端口归零 → start → 等健康）
python scripts/vm_ssh.py -f scripts/verify_milvus_autostart.sh
```

> ⚠️ `docker-compose` 是 **v1**（`/usr/local/bin/docker-compose`，Python 版），
> 这个 VM 上**没有** `docker compose` v2 插件，写脚本时别用 v2 的写法。
>
> 实测验证记录（`verify_milvus_autostart.sh`）：
> ```
> systemctl stop  → is-active: inactive，19530 监听数 0
> systemctl start → is-active: active
> 第 15 秒：9091 healthz OK ✅，19530 监听数 2
> ```

**日常运维命令**

```bash
systemctl status milvus          # 看状态
systemctl restart milvus         # 重启向量库（改完 compose 后要执行）
docker logs -f milvus-standalone # 看 Milvus 日志
```

## 7. GPU 用在哪里

N 卡只服务于 **Python 侧的两个本地模型**，和 Milvus、MySQL 无关：

| 用途 | 模型 | 显存 | 说明 |
|---|---|---|---|
| 向量化 | BGE-M3 | ≈ 2.5 GB | 文档入库时批量编码 |
| 图片 OCR | PaddleOCR PP-OCRv5 | ≈ 1.5 GB | 照片识别上传 |
| *（可选）* 本地 LLM | Ollama / vLLM | 视模型而定 | 当前走云端，暂不需要 |

**前提**：Python 必须跑在**有 N 卡驱动和 CUDA 的那台机器上**。
- 若 Python 跑在 Windows 宿主机 → 装 CUDA 版 PyTorch（`pip install torch --index-url https://download.pytorch.org/whl/cu124`）
- 若 Python 跑在 Linux 虚拟机 → 虚拟机需要开启 GPU 直通（VMware 的 3D 加速不够用），或改用 `nvidia-container-toolkit` 跑容器

这个问题的答案决定了整个部署形态，见第 9 节。

## 8. 环境自检清单

`beibei-agent` 提供 `GET /api/v1/health`，首页「环境自检」面板会显示这 8 项：

| # | 检查项 | 失败时的表现 |
|---|---|---|
| 1 | MySQL 连接 + `beibei` 库存在 + 21 张表齐全 | 后端启动即失败 |
| 2 | Milvus 连接 + collection 存在 | 文档入库不可用 |
| 3 | BGE-M3 模型已下载并能编码 | 文档入库不可用 |
| 4 | PaddleOCR 模型已下载 | 图片上传不可用 |
| 5 | ffmpeg 可执行 | 语音转文字不可用 |
| 6 | DeepSeek API Key 有效 | 出题与判分不可用 |
| 7 | 讯飞/阿里 ASR 凭据有效 | 语音输入不可用 |
| 8 | 磁盘剩余空间 > 5 GB | 提示清理 |

**每项可单独降级**：ASR 不可用就隐藏录音按钮，OCR 不可用就禁用图片上传，而不是整个系统起不来。

## 9. 实测结论（已在开发机验证）

### 9.1 部署形态 —— 确定

> **Java 和 Python 都跑在 Windows 宿主机**（也就是 IDEA / PyCharm 所在的这台机器），
> 通过 `192.168.1.100` 访问 Linux 虚拟机里的 MySQL 与 Milvus。
>
> 原因：N 卡在宿主机上（RTX 4060 Laptop）。VMware 对笔记本独显几乎没有可用的直通方案，
> 把 Python 放进虚拟机等于放弃 GPU，BGE-M3 和 PaddleOCR 会退回 CPU 慢 3~5 倍。

```
┌───────────────── Windows 宿主机 ─────────────────┐        ┌──── Linux 中间件主机 ────┐
│  IDEA  → beibei-server   :8080                   │        │  milvus-standalone :19530│
│  PyCharm → beibei-agent  :8000  ── GPU: RTX4060  │ ─────> │  mysql:8.0.29      :3306 │
│  浏览器  → localhost:8080                         │        │  redis:7.0.0       :6379 │
└──────────────────────────────────────────────────┘        └──────────────────────────┘
```

### 9.4 🔴 两个必须先处理的问题

**问题 1：Python 环境 —— 建议建独立 conda 环境（3.11）**

实测 PyPI 上关键包对 Windows 的 wheel 覆盖情况：

| 包 | 最新版 | Windows wheel 支持的 Python |
|---|---|---|
| `paddlepaddle` | 3.3.1 | cp39 / cp310 / cp311 / cp312 / **cp313** |
| `torch` | 2.14.0 | cp310 ~ **cp314** |
| `paddleocr` | 3.7.0 | 纯 Python 包 |
| `sentence-transformers` | 6.0.1 | 纯 Python 包 |

所以系统的 **Python 3.13.9 其实是能装的**。仍然建议建独立环境，理由是：不污染系统 Python，
依赖冲突时可以整体删掉重建，而且 3.11 是当前 AI 生态踩坑最少的版本。

```powershell
conda create -n beibei python=3.11 -y
conda activate beibei
python -V        # 应为 3.11.x
conda info --envs   # 拿到环境路径，填进 PyCharm 的 Interpreter
```

> ⚠️ **pymilvus 版本必须锁死**：装 `pymilvus>=2.5.4,<2.6`。
> PyPI 最新的 3.0.1 是面向 **Milvus 3.0** 的，连你的 2.5.23 会不兼容。

**问题 2：E 盘只剩 6.9 GB —— 模型和虚拟环境必须挪到别的盘**

实测磁盘剩余：C 16.2 GB ／ D 69.7 GB ／ **E 6.9 GB** ／ F 51.4 GB。
而需要占用的空间：

| 内容 | 体积 |
|---|---|
| conda 环境 + CUDA 版 PyTorch | ≈ 5~8 GB |
| BGE-M3 模型权重 | ≈ 2.3 GB |
| PaddleOCR 模型 | ≈ 0.5 GB |
| Maven 本地仓库（IDEA 默认在 C 盘用户目录） | ≈ 1 GB |

**结论**：E 盘放代码完全没问题（代码 + 文档只有几百 KB），但下面这些必须改到 D 盘或 F 盘：

```powershell
# 模型缓存目录
[Environment]::SetEnvironmentVariable('HF_HOME','D:\ai-models\hf','User')
[Environment]::SetEnvironmentVariable('MODELSCOPE_CACHE','D:\ai-models\modelscope','User')
# conda 环境目录
conda config --add envs_dirs D:\conda-envs
```

上传的学习资料也建议落到 D 盘：`beibei.upload.dir: D:/beibei-data/upload`（配置项 `upload.dir`）。
