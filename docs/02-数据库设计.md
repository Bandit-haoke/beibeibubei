### 2.16 `bb_resume` 简历库（M6）

`id, user_id, file_name, file_path, file_size, file_type, raw_text(longtext 解析全文), char_count, profile_json(json AI 结构化档案), target_position, status(0 待解析 1 解析中 2 就绪 3 失败), error_msg, created_at, updated_at`

**与其他表最不一样的地方：这张表刻意孤立。**
简历不进 Milvus 分块集合、不建知识点树、不参与 RAG 检索。
原因：简历不是「要背的材料」，混进学习库会污染检索结果与掌握度统计。

`profile_json` 结构（由 `RESUME_PARSE` 模板产出）：

```json
{
  "name": "", "years": 0, "education": "", "school": "", "major": "",
  "currentCompany": "", "currentTitle": "", "targetPosition": "",
  "skills": ["Redis", "Spring Boot"],
  "projects": [{ "name": "", "role": "", "period": "",
                 "techStack": [], "highlights": [], "evidence": "简历原文原话" }],
  "workExperience": [{ "company": "", "title": "", "period": "", "duty": "" }],
  "selfEvaluation": "", "highlights": [],
  "risks": ["简历里含糊或可疑、面试官该重点追问的点"]
}
```

> `evidence` 是「可追溯」的关键：每个项目都留了简历原话，
> 面试官追问时能引用原文，评分时也能拿它做简历一致性核对。

### 2.17 `bb_interview` 模拟面试场次（M6）

`id, user_id, resume_id, kb_id(可空，关联学习知识库用于出题), job_title, difficulty(1 初级 2 中级 3 高级), max_turns(计划轮数 8~12), turn_count, status(0 待开始 1 进行中 2 已结束 3 失败), total_score(decimal 5,2), summary, report_json(json), created_at, started_at, finished_at`

对话内容**不在这张表**（在 `bb_interview_turn`），这里只放一场面试的元信息与最终报告。

`report_json` 结构：

```json
{
  "overallScore": 0, "summary": "",
  "dimensions": [{ "name": "", "score": 0, "comment": "" }],
  "strengths": [],
  "weakPoints": [{ "skill": "", "level": "", "evidence": "", "suggestion": "" }],
  "knowledgePoints": ["标准技术术语，直接拿去出题"],
  "nextSteps": [],
  "turnScores": [{ "seq": 1, "score": 0 }]
}
```

> `knowledgePoints` 特意要求「标准技术术语、每条不超过 20 字、不要写句子」，
> 因为它的下游是 `bb_tag` 的名字匹配 —— 写成句子就匹配不上了。

### 2.18 `bb_interview_turn` 面试对话轮次（M6）

`id, interview_id, seq, role(1 面试官 2 候选人), content, question_type(INTRO/PROJECT/TECH/FOLLOWUP/SCENARIO/BEHAVIOR), based_on, expects(json), score(decimal 5,2), feedback_json(json), created_at`

一次「问答」= 两行。面试官那行带 `based_on` 与 `expects`，回答那行带 `score` 与 `feedback_json`。

**可追溯性就落在这张表上**：
- 每个问题都能回答「为什么问这个」→ `based_on` 指向简历里的具体一段；
- 每个分数都能回答「凭什么给这个分」→ `feedback_json` 里是五维明细与点评。

`feedback_json` 结构：

```json
{
  "score": 0,
  "scores": { "techAccuracy": 0, "specificity": 0, "structure": 0,
               "consistency": 0, "relevance": 0 },
  "dimensionLabels": { "techAccuracy": "技术准确性", "...": "..." },
  "goodPoints": [], "problems": [], "suggestion": "",
  "contradiction": "与简历矛盾时填这里，并引用简历原话",
  "followUpNeeded": true
}
```

> `consistency`（与简历一致性）是面试模块独有的维度。
> 学习题目的答案有原文依据，客观题能 100% 程序化判分；
> 面试没有标准答案，唯一能硬核核对的就是「你嘴上说的和简历写的是否对得上」。

## 3. Milvus 集合设计

### 原则

- **按 embedding 模型分 collection**：`bb_chunk_bge_m3`
- **按知识库分 partition**：`partition = kb_{kbId}`，检索时指定 partition，天然隔离、召回更准
- 题目查重用**独立 collection**：`bb_question_bge_m3`

### `bb_chunk_bge_m3` 字段

| 字段 | 类型 | 说明 |
|---|---|---|
| pk | Int64 (auto_id=false) | 与 `bb_doc_chunk.milvus_pk` 一一对应 |
| vector | FloatVector(dim=1024) | BGE-M3 稠密向量维度 1024 |
| doc_id | Int64 | 标量，可按文档过滤 |
| kb_id | Int64 | 标量 |
| chunk_index | Int64 | |
| tag_ids | Array<Int64> | 知识点 ID，支持按知识点过滤检索 |

索引：`IVF_FLAT` / `HNSW`，metric `COSINE`。数据量 < 100 万用 `HNSW(M=16, efConstruction=200)` 即可。

### 一致性约定

- MySQL 的 `bb_doc_chunk` 是**主数据**，Milvus 是**索引副本**。
- 删除文档：先删 Milvus 向量，再删 MySQL 分块（或标记删除 + 后台清理），提供「向量库与 MySQL 一致性校验」运维接口。
- 重建：embedding 模型升级时**必须新建 collection** 并全量重跑，不允许在原 collection 上追加。

## 4. 关键索引与性能约定

- 所有列表查询必须带 `kb_id`，且走覆盖索引。
- 全文检索需求（关键词搜原文）用 MySQL 的 `FULLTEXT` 索引加在 `bb_doc_chunk.content` 上（`WITH PARSER ngram`，中文必需），与向量检索做**混合召回**。
- `bb_ai_call_log` 增长最快，超过 50 万行时按 `created_at` 做归档表。
- 分页统一 `LIMIT/OFFSET` 即可（单人使用，数据量小），不做深度分页优化。
