# 背备不悲 · 设计文档

> 版本 v0.1（立项稿）｜项目代号 `beibei`｜单人本机部署

---

## 1. 项目定位

**背备不悲** 是一个本地部署的 AI 背书助手。它解决的核心痛点是：

> 手上有大量学习资料（JavaWeb 讲义、教材 PDF、老师发的 Word、自己拍的书页照片），
> 但"看一遍"不等于"背下来"，而自己出题、自己批改的成本又太高。

产品把「资料 → 知识库 → 出题 → 作答 → 判分 → 复习」这条链路全部自动化，并且**所有题目、答卷、错题都固化在数据库里**，下次打开继续用，不是一次性的玩具。

**不是什么**：不是通用聊天机器人，不是笔记软件，不做多人协作（当前阶段）。

**核心闭环**：
```
上传资料 → 解析入库(RAG) → AI 出题并固化 → 作答(可语音) → AI 按要点判分
    ↑                                                              │
    └──────────── 错题本 + 艾宾浩斯复习计划 ←────────────────────────┘
```

## 2. 总体架构

### 2.1 分层

| 层 | 模块 | 技术选型 | 说明 |
|---|---|---|---|
| 表现层 | `beibei-web` | Vue 3 + Vite 5 + TypeScript + Pinia + Vue Router + Element Plus + ECharts + axios | 构建产物输出到 `beibei-server/src/main/resources/static/`，由 Java 托管 |
| 应用层 | `beibei-server` | Spring Boot 3.3.x、Java 21、MyBatis-Plus 3.5、Sa-Token、Knife4j、RestClient、SseEmitter、Hutool、Lombok | 唯一对外网关；所有鉴权、事务、任务调度在这里 |
| 智能层 | `beibei-agent` | Python 3.11、FastAPI、uvicorn、Pydantic v2、LangGraph、SQLAlchemy 2.0、pymilvus、httpx、tenacity | 只在内网暴露，靠 `X-Internal-Token` 校验 |
| 存储层 | MySQL 8.0 | 业务数据、题库、答卷、错题、日志 | 表前缀 `bb_` |
| 存储层 | Milvus 2.4 | 文档分块向量 | 按 embedding 模型分 collection，按知识库分 partition |
| 外部 | 云端 AI | LLM（对话/出题/判分）、ASR（语音转写） | 统一适配层，界面可切换 |
| 本地模型 | Embedding / OCR | BGE-M3、PaddleOCR | **不依赖云端，不入切换列表** |

### 2.2 Java ↔ Python 的调用约定

- 协议：HTTP + JSON，长任务走 **SSE 流式**。
- 鉴权：Java 在 Header 带 `X-Internal-Token: <共享密钥>`，Python 侧中间件校验，不匹配直接 401。
- 方向：**只有 Java 主动调 Python**。Python 需要回写数据时，直接连同一个 MySQL 写 AI 相关表（见数据库设计），不反向调 Java 接口，避免循环依赖。
- 超时与重试：Python 侧对 LLM 调用用 `tenacity` 做指数退避重试（最多 3 次）；Java 侧对 Python 调用超时 120s（出题/判分这类长任务改为异步任务 + SSE，不走同步等待）。
- 降级：Python 服务不可用时，Java 返回明确的"智能体未启动"提示，而不是 500。

### 2.3 长任务处理模型

文档解析、批量出题、批量判分都可能跑几十秒到几分钟。统一走异步任务：

```
前端提交 → Java 写 bb_async_task(status=PENDING) 并立即返回 taskId
        → Java 异步线程调 Python（SSE 流式）
        → Python 边跑边推进度，Java 转发并落库 progress
        → 前端订阅 GET /api/task/{taskId}/stream 拿实时进度
        → 结束后 Python 落业务数据，Java 更新 task(status=SUCCESS) 并返回结果 ID
```

### 3.5 后期新增需求（M6 · AI 模拟面试）

> 需求原话：「再添加一个功能，上传自己的简历，由 AI 模拟面试官来面试，用户来回答」
>
> 定位：这是**输出侧**的能力。前面 F1~F32 解决的是「把材料变成题、把题刷对」，
> 这一块解决的是「把知识讲出来」——面试考的不是你记不记得，而是你能不能讲清楚。

| 编号 | 功能 | 说明 |
|---|---|---|
| F33 | 简历库 | 上传 PDF/Word 简历或粘贴文字，AI 抽取结构化档案（技能 / 项目经历 / 工作经历 / **待核实点**）。与学习知识库**完全隔离**，不进 Milvus、不建知识点树 |
| F34 | 多轮对话面试 | AI 面试官按「自我介绍 → 项目深挖 → 原理考察 → 含糊处追问」的策略逐轮提问，8~12 轮；每个问题都标注题型与「依据简历哪一段」 |
| F35 | 逐轮五维评分 | 技术准确性 / 项目具体性 / 表达结构 / **与简历一致性** / 岗位匹配度。回答后实时出分与点评，不用等最后 |
| F36 | 评估报告 | 总分、维度雷达、逐轮得分曲线、优势、薄弱项（带面试中的具体证据）、优先补的知识点、下一步建议 |
| F37 | 薄弱点闭环 | 报告里的知识点 → 匹配学习知识库的标签 → 一键生成专项题卷，直接回到学习模块去刷 |

**关键设计说明**

- **为什么要「与简历一致性」这一维**：学习题目的答案有原文依据，客观题能 100% 程序化判分；
  面试没有标准答案，唯一能硬核核对的就是「你嘴上说的和简历写的是否对得上」。
  这是模拟面试相对于「和 AI 随便聊聊」唯一不可替代的价值。
- **为什么要留「待核实点」**：简历里「精通 XX」「主导整体架构」这类表述是面试官最该追问的地方。
  AI 抽取档案时把这些标出来，提问策略会优先围绕它们展开。
- **为什么报告要输出「标准技术术语」而不是句子**：下游是 `bb_tag` 的名字匹配，
  写成句子就匹配不上，闭环就断了。

## 4. 核心流程设计

### 4.1 文档入库流程（上传 → 可检索）

```
1. 前端上传 → Java 存到 ./data/upload/{kbId}/{uuid}.{ext}，写 bb_document(status=UPLOADED)
2. Java 建异步任务，调 Python POST /api/v1/ingest
3. Python：
   a. 按类型解析：PDF→PyMuPDF（扫描版检测到无文本层则转 OCR）/ docx→python-docx /
      pptx→python-pptx / 图片→PaddleOCR
   b. 清洗：去页眉页脚、去多余空行、合并断行、保留标题层级与页码定位
   c. 分块：按标题层级优先切，超长块再按 token 数(500~800)滑窗重叠(15%)
      每块记录 {chunk_index, page_no, section_path, char_start, char_end}
   d. 知识点抽取：把全文大纲喂给 LLM，产出层级知识点树（≤3 层），落 bb_tag
   e. 分块打标：每块挂 1~3 个知识点 tag（可用向量相似度预筛 + LLM 确认）
   f. 向量化：BGE-M3 批量编码 → 写入 Milvus，partition = kbId
   g. 分块原文与 Milvus 主键写 bb_doc_chunk
4. Python 回调更新任务进度，Java 更新 bb_document(status=READY, chunk_count)
```

### 4.2 出题流程

```
1. 前端选：知识库、范围（全部 / 指定知识点）、题量(10/20/30/自定义)、题型配比、难度配比
2. Java 建 bb_paper(status=GENERATING) + 异步任务，调 Python POST /api/v1/generate-questions
3. Python 按知识点分组，每组抽样检索相关分块（RAG），构造 prompt
4. LLM 输出强约束 JSON（Pydantic 校验，失败自动重试 ≤3 次）
5. 自检 Agent：逐题验证「题干+答案能否在召回分块中支撑」，不通过则丢弃并补生成
6. 查重：与 bb_question 已有题目向量比对，相似度 > 0.92 丢弃
7. 落库：bb_question(status=DRAFT) + bb_question_option + bb_question_tag + bb_paper_item
8. 前端进入审核页：通过 / 编辑 / 删除 / 重新生成 → 通过后 status=PUBLISHED
```

### 4.3 答题与判分流程

```
1. 前端拉取题卷（已发布题目）
2. 用户作答：
   - 打字直接输入
   - 语音：MediaRecorder 录 webm/opus → 上传 → Java 转 Python → ffmpeg 转 16k 单声道 PCM
     → 讯飞/阿里 ASR → 返回文本 → 填入输入框（用户仍可编辑）
3. 交卷 → Java 写 bb_exam_record(status=SUBMITTED) + bb_answer_item(逐题)
4. 客观题（单选/多选/判断）：程序直接判定，不走 AI，省 Token
5. 主观题（填空/名词解释/简答/论述/代码题）：
   a. 取题目 + rubric 要点 + 关联分块原文
   b. LLM 按要点评分：命中要点的序号、漏掉的要点、多余的错误表述
   c. 输出结构化结果 + 引用到具体 chunk（前端可点击跳转原文）
   d. 代码题额外做语义正确性检查（不跑编译，靠 LLM 读代码 + 关键 API 是否用对）
6. 汇总总分 → 更新 bb_exam_record
7. 判错/低于阈值的题写入 bb_mistake，计算 next_review_at
```

**题型 → 判分方式映射**

| 题型 | 判分方式 | 是否耗 Token |
|---|---|---|
| 单选 / 多选 / 判断 | 程序比对 | 否 |
| 填空 | 先精确/同义词表匹配，未命中交 AI | 部分 |
| 名词解释 / 简答 / 论述 | AI 要点法（Rubric） | 是 |
| 代码题 | AI 读代码检查关键点 | 是 |
| 口述复述 | AI 对照原文算覆盖度 | 是 |

### 4.4 复习流程（艾宾浩斯）

```
SM-2 简化实现：
  grade 0~5（由本次得分率映射）
  答对：repetitions+1，interval = interval==0 ? 1 : interval==1 ? 6 : round(interval*ease)
  答错：repetitions=0，interval=1
  ease_factor 初始 2.5，答得好 +0.1，答得差 -0.2，下限 1.3
  next_review_at = now + interval 天
首页展示「今日待复习」列表 → 进入复习模式（只出题不重新生成）→ 结果回写错题本
```

### 4.5 模拟面试流程（M6）

```
1. 上传简历 → Java 落盘 + 建异步任务 → Python /api/v1/resume-parse（SSE）
   a. parsing.parse() 解析全文（PDF 扫描件走 OCR）
   b. LLM RESUME_PARSE 抽结构化档案，**每条项目都留 evidence（简历原话）+ risks（待核实点）**
   c. 写回 bb_resume.profile_json，status=2 就绪

2. 新建面试 → bb_interview(status=0) → Python /interview/start（同步）
   a. LLM INTERVIEW_ASK：第 1 题固定自我介绍
   b. 落 bb_interview_turn(role=1, based_on, expects)，status=1 进行中，turn_count=0

3. 逐轮问答（循环 max_turns 次）
   a. 用户作答（打字或语音转写）
   b. LLM INTERVIEW_EVAL → 五维评分 + 点评 + contradiction（与简历矛盾处）
   c. 落 bb_interview_turn(role=2, score, feedback_json)，turn_count+1
   d. 未到轮数上限 → LLM INTERVIEW_ASK 出下一题（含糊处优先 FOLLOWUP）→ 回到 a
   e. 到上限 → 返回 finished=true，前端引导出报告

4. 生成报告 → LLM INTERVIEW_REPORT（读整场转录）
   落 bb_interview.report_json + total_score + summary，status=2 已结束

5. 联动出题
   报告 knowledgePoints → 在 bb_tag 里按名字双向包含匹配 → 命中 tagIds
   → 复用 PaperService.generate() 现有出题流水线 → 得到一张专项题卷
   → 匹配不到就退化成整库出题，并在响应 message 里说明
```

**为什么只有第 1 步走 SSE**：扫描件 PDF 走 OCR，几十秒到几分钟很正常，必须异步推进度。
第 3、4 步一次就是一次 LLM 调用，几秒钟的事，加进度条反而让前端状态机复杂一倍。

## 5. 硬性设计约束（踩了就翻车，写进代码规范）

### 约束 0：简历与学习知识库必须物理隔离

简历**不进** Milvus 分块集合、**不建**知识点树、**不参与** RAG 检索，
只存在 `bb_resume` 自己的表里。

唯一的跨界通道是「面试报告的薄弱知识点 → 按名字匹配 `bb_tag` → 复用出题流水线」。
理由：简历不是「要背的材料」。混进学习库会污染检索结果与掌握度统计，
而且简历里全是个人信息，和学习资料的检索空间本来就不该共享。

### 约束 1：Embedding 模型与 LLM 厂商必须解耦

切换 GPT / Claude / 通义 / DeepSeek **绝不能**影响向量。不同 embedding 模型产出的向量空间不可比，一旦混用，同一个知识库里新旧向量无法一起检索，RAG 直接失效。

**落实方式**：
- `bb_knowledge_base` 上固定一个 `embedding_model` 字段，创建知识库时确定，之后不可改（要改只能新建知识库重新入库）
- Milvus **按 embedding 模型分 collection**（`bb_chunk_bge_m3`），collection 内**按知识库分 partition**
- LLM 厂商配置只作用于「出题 / 判分 / 分类」三类生成任务

### 约束 2：语音必须走服务端 ASR，不要用浏览器 Web Speech API

已定方案：云端厂商 ASR。要点：
- 前端 `MediaRecorder` 默认输出 **webm/opus**，讯飞/阿里多数接口要 **16k 单声道 PCM/WAV**，中间必须 **ffmpeg 转码**（所以 Python 侧要装 ffmpeg 并在启动时自检）
- 短句（<60s）走"一句话识别"HTTP 接口即可，实现最简单
- 想边说边出字，后期再上 WebSocket 流式识别
- ASR 失败时前端必须降级为可编辑的空白输入框 + 明确报错，不能卡死作答流程

### 约束 3：AI 出的题必须人工审核才能用

`bb_question.status` 三态：`DRAFT`（AI 生成待审）→ `PUBLISHED`（可用）→ `DISABLED`（停用）。组卷只捞 `PUBLISHED`。没有这一步，题目质量会迅速崩坏。

### 约束 4：判分必须可解释、可申诉

任何 AI 打分都要返回三个东西：**得分、要点命中明细、原文引用**。缺少引用链的判分不落库。同时保留 `appeal_*` 字段支持重判。

### 约束 5：Java 是唯一对外网关

前端不得直连 Python 端口。所有跨语言调用带 `X-Internal-Token`。Python 只写 AI 相关表，业务表由 Java 独占写。

### 约束 6：前端不要用 `file://` 双击打开

原因：
- `file://` 下请求的 `Origin` 是 `null`，跨域配置容易踩坑
- 一旦涉及麦克风（本产品必用），浏览器有安全上下文限制；虽然 Chrome 对 `file://` 宽松，但换浏览器就崩

**正确做法**：前端构建产物放进 `beibei-server/src/main/resources/static/`，访问 `http://localhost:8080`。想要"双击即用"的体验，就写 `scripts/一键启动.bat` 拉起所有服务并自动 `start http://localhost:8080`。

## 7. 风险与待确认

| 风险 | 影响 | 应对 |
|---|---|---|
| **Milvus 在 Windows 需要 Docker Desktop 或 WSL2** | 装不上就跑不起来 | 确认本机是否已装 Docker Desktop；若不想装 Docker，可退回 **Milvus Lite**（需 WSL）或改用 Qdrant 单 exe。**这是当前第一阻塞项，请确认** |
| 云端 ASR 需要讯飞/阿里账号与 Key | 语音功能不可用 | 先做打字作答，语音作为可插拔能力，无 Key 时自动隐藏录音按钮 |
| 浏览器录音格式需 ffmpeg 转码 | 转写失败 | Python 启动时自检 ffmpeg，缺失则日志明确提示并提供下载指北 |
| AI 判分主观性强、可能有争议 | 用户不信任 | 要点法 + rubric 可编辑 + 引用原文 + 申诉重判，四件套一起上 |
| LLM 出题质量不稳定 | 题海垃圾 | 审核工作流 + 自检 Agent + 查重，三道闸门 |
| 出题消耗 Token 快 | 成本失控 | 题目固化复用、按任务路由模型、相似度查重、成本看板 |
| 单人本地开发三端并行 | 容易烂尾 | 按里程碑推进，每个阶段都有可运行产物 |
| 长文档（>200 页）解析慢 | 体验差 | 异步任务 + SSE 进度条 + 可中断 |

### 需要你确认的信息

1. **是否已安装 Docker Desktop？**（决定 Milvus 怎么部署，是第一阻塞项）
2. 本机是否有 **NVIDIA 显卡**？（决定 BGE-M3 / PaddleOCR 跑 CPU 还是 GPU，CPU 也能跑但慢 3~5 倍）
3. 是否已有 **讯飞或阿里的账号与 Key**？
4. 打算先接哪家 LLM？（建议 **DeepSeek**：便宜、中文好、OpenAI 兼容协议，适配层写完其他家基本是改 base_url）
5. 有没有**真实资料样本**可以拿来测？（给一份 JavaWeb 的 Word/PDF，我可以用它调 prompt 和分块策略，效果差别很大）
