## 三种启动方式

### 方式一：一键启动（推荐日常用）

双击 `scripts\一键启动.bat`，或：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\一键启动.ps1
```

它会依次做：检查虚拟机中间件 → 起 Python → 起 Java → 打开 <http://localhost:8080>。
两个服务各跑在独立窗口里，关窗口即停止。停止用 `scripts\停止.ps1`。

### 方式二：IDE 里跑（开发时用）

| 模块 | IDE | 怎么跑 |
|---|---|---|
| `beibei-agent` | **PyCharm** | 打开 `beibei-agent` 目录 → Interpreter 选 `D:\conda-envs\beibei\python.exe` → 右键 `run.py` → Run |
| `beibei-server` | **IDEA** | 打开 `beibei-server` 目录 → 等 Maven 导入 → 运行 `BeibeiApplication` |

> IDEA 提示：Settings → Build Tools → Maven 里确认 **User settings file** 指向
> `<你的用户目录>\.m2\settings.xml`（这样才能用到 D 盘仓库和阿里云镜像）。

### 方式三：纯命令行

```powershell
# Python
cd beibei-agent; D:\conda-envs\beibei\python.exe run.py

# Java
cd beibei-server; D:\java\bin\java.exe -jar target\beibei-server-0.1.0.jar
```

## 踩过的坑（避免重复踩）

### 🔴 最重要的一条：镜像源要按「大文件」实测，不能只看首页响应

这条网络上，**不同镜像对大文件的下载速度差 500 倍以上**：

| 源 | 实测速度 | 结论 |
|---|---|---|
| **腾讯云 PyPI** | **44.47 MB/s** | ✅ 首选，118 MB 的 torch 只用 2.7 秒 |
| **ModelScope** | **28.3 MB/s** | ✅ 模型权重的首选，2.1 GB 只用 76 秒 |
| huaweicloud | 6.60 MB/s | ⚠️ 可用 |
| 阿里云 PyPI | 0.07 MB/s | ❌ 大包几乎不动 |
| pypi.org 直连 | 0.04 MB/s | ❌ |
| download.pytorch.org | 连接建立但数据不流动 | ❌ CDN 在国内卡死 |
| 阿里云 pytorch-wheels | 0.06 MB/s | ❌ |
| 清华 PyPI | HTTP 403 | ❌ 被拦 |
| GitHub | 80 MB 的 ffmpeg 下了 1 小时没完 | ❌ |

**教训**：一开始用「首页响应时间」挑镜像（阿里云 209ms 最快）就选错了。
真正该测的是**下载 4 MB 实际数据用了多久**。本项目的 `scripts/vm_ssh.py` 旁边
留了这种测速代码的写法（HttpWebRequest + AddRange + Stopwatch）。

### 其他坑

| 坑 | 现象 | 解法 |
|---|---|---|
| **`your-vm-password` 不是 MySQL 密码** | `Access denied for user 'root'@'192.168.1.1'` | MySQL 真实密码是 `your-mysql-password`（`docker inspect mysql` 得到）。`your-vm-password` 是 Linux 账号和 Redis/RabbitMQ 的 |
| **`JAVA_HOME` 被用户级变量覆盖成不存在的路径** | Maven 报 `JAVA_HOME environment variable is not defined correctly` | 用户级 `JAVA_HOME` 指向 `E:\Develop\yonyou-yds\...jdk21.0.7-win_x64`（不存在），覆盖了机器级的 `D:\java`。已改为 `D:\java` |
| **PowerShell 的 `Set-Content -Encoding UTF8` 会写 BOM** | Java 编译报 `非法字符: '\ufeff'` | 用它生成 Java 源码后必须去 BOM（`[System.IO.File]::WriteAllText` + `UTF8Encoding($false)`） |
| **Java 不支持 `import ... as` 别名** | `需要';'` 编译错误 | 用全限定名 `@io.swagger.v3.oas.annotations.tags.Tag(...)`，或换类名避开冲突 |
| **MyBatis-Plus 全局 `table-prefix` 与 `@TableName` 叠加** | 表名会变成 `bb_bb_xxx`（潜在风险） | 不用全局前缀，每个实体显式写 `@TableName("bb_xxx")` |
| **axios 默认 `Content-Type: application/json` 破坏文件上传** | 上传 FormData 时后端解析失败 | 不设默认 Content-Type，交给 axios 按数据类型推断 |
| **AI 出的 JSON 里含字面量大括号，`str.format` 会炸** | 出题模板渲染抛 KeyError | Prompt 渲染改成「只替换已知变量名」，不碰其它花括号 |
| **Windows 控制台 GBK 编码** | Python 脚本 print ✓ 时 `UnicodeEncodeError: 'gbk' codec` | 脚本内 `sys.stdout.reconfigure(encoding="utf-8")`，命令里设 `$env:PYTHONIOENCODING='utf-8'` |
| **PowerShell 拆坏 `-Dfile.encoding=UTF-8`** | `ClassNotFoundException: /encoding=UTF-8` | 用数组传参 `& java @('-Dx=y','-jar',$jar)`，或干脆去掉（Java 18+ 默认 UTF-8） |
| **后台进程继承不到新设的环境变量** | `PIP_CACHE_DIR` 没生效，pip 写到了 C 盘缓存 | 在命令里显式 `$env:PIP_CACHE_DIR = 'D:\cache\pip'` |
| **npm 11 的 allow-scripts 拦截** | esbuild postinstall 没跑 | 实测不影响 `vite build` |
| **阿里云 Maven 镜像只留最新版** | 3.9.9 下载 404 | 用 3.9.16 |
| **pymilvus 版本** | — | **必须 `>=2.5.4,<2.6`**。PyPI 最新的 3.x 面向 Milvus 3.0，连 2.5.23 不兼容 |
| **ffmpeg 从 GitHub 下不动** | 80 MB 下一小时没完 | 改用 `pip install imageio-ffmpeg`，包里自带 ffmpeg 7.1 二进制，复制到 `D:\tools\ffmpeg\bin` 即可 |

### M2 阶段踩的坑（都已修复）

| 坑 | 现象 | 解法 |
|---|---|---|
| **Spring 循环依赖** | `PaperService ↔ GenerationRunner`，应用启动直接失败 | 把状态收尾抽成 `PaperStatusService`，依赖变单向 |
| **MySQL: DISTINCT 下 ORDER BY 列必须在 SELECT 列表** | 报 3065，出题第一步就挂 | 改用 `EXISTS` 子查询替代 `JOIN + DISTINCT` |
| **Milvus 不支持部分字段 upsert** | `Insert missed an field 'vector'`，打标结果一直写不进 Milvus | **顺序错了** —— 改成「先打标、再带着 tag_ids 一次 insert」，彻底不需要回填 |
| **模板变量缺失时 `re.findall(pattern, None)` 抛 TypeError** | 被外层 try/except 吞掉，表现为「静默生成 0 道题」 | `_parse_text_field` 兼容 `【label】` 与 `label：` 两种写法，调用方兜底 `or ""` |
| **`_expand_ratio` 只接受 dict** | Java 侧传的是 JSON 列表，`.items()` 抛异常同样被吞 | 同时支持列表与字典；题型/难度各用各的别名表 |
| **干扰项从代码块中间截断** | 出现 `` ` 并由 JDBC 设置参数 `` 这种碎片 | 切句时要求至少 8 个汉字；`_shorten` 去掉首尾代码符号 |
| **题目只挂最细子标签** | 用户按顶层章节筛选查不到任何题 | 落库时把题目继承分块的标签 **并补全所有祖先标签** |
| **「材料不足就悄悄补充全库」** | 用户选第一章，却出了 MyBatis 的题 | 去掉静默扩范围；只在范围内**完全没材料**时才退回全库，并在进度里说明 |

### SM-2 实现说明

```
答对：repetitions+1
      interval = repetitions==1 ? 1 : repetitions==2 ? 6 : round(interval × ease)
      ease += 0.1
答错：repetitions=0，right_streak=0，interval=1，ease = max(1.30, ease - 0.2)
next_review_at = now + interval 天
连续答对 ≥4 次且间隔 ≥30 天 → 标记「已掌握」，移出待复习队列
```

实测第一次答对后间隔仍是 1 天、第二次才涨到 6 天 —— 这是**标准 SM-2 行为**，
不是 bug（我一开始的测试文案写错了，已修正）。

| **`list_partitions` 返回 `List[str]` 而不是 `List[dict]`** | 分区永远建不出来，写入时报 `partition not found[kb_2]`；异常被 except 吞掉，表现为静默失败 | 写了 `partition_names()` 统一兼容 str/dict/对象三种形态 |
| **Milvus 默认一致性 Bounded** | 入库成功但立刻检索召回 0 条 | 入库后 `flush()` + 检索时 `consistency_level="Strong"` |
| **`drop_partition` 报 partition is loaded** | 删除知识库时分区删不掉 | 先 `release_partitions()` 再 `drop_partition()` |
| **paddlepaddle 3.3.x 的 PIR + oneDNN bug** | OCR 抛 `NotImplementedError: ConvertPirAttribute2RuntimeAttribute not support` | `PaddleOCR(enable_mkldnn=False)` |
| **PaddleOCR 3.x 的 `OCRResult` 是 dict 子类** | `rec_texts` 在顶层，不在 `.json["res"]` 里，按文档写会取不到 | 实测确认后改成顶层取值 |
| **PaddleOCR 3.x 的 `ocr()` 不接受 `cls` 参数** | 3.x 环境里回退到 2.x 代码路径会抛 TypeError | 有 `predict()` 就只走 predict，不再回退 |
| **paddle 与 torch 并发安装导致 DLL 锁** | `OSError: Error loading torch\lib\shm.dll` | 串行安装；必要时 `pip install --force-reinstall --no-deps torch` |
| **paddle 把 numpy 从 2.4.6 降到 2.3.5** | 一度以为 ABI 冲突 | 实测 torch 仍正常，无需处理 |

### 三个设计决策（已确认）

| 决策点 | 选择 | 理由 |

### 面试官怎么问（`INTERVIEW_ASK` 的出题策略）

写进 Prompt 的硬规则，避免聊成「随便侃」：

1. 第 1 轮固定自我介绍；
2. 之后顺着简历里的项目做**深度追问**：为什么这么设计、遇到什么问题、怎么解决、有没有量化结果；
3. 每 3 轮穿插一道原理/八股题，验证基础是否扎实；
4. 候选人上一轮**含糊（只给结论不给过程）就优先追问那个点**，类型标 `FOLLOWUP`；
5. 不重复已问过的问题，一次只问一个。

每个问题都带 `basedOn`（对应简历里的哪一段原话）——这是「可追溯」在面试场景的落地：
用户随时知道面试官为什么问这个，而不是感觉被随机刁难。

### 评分维度（与学习题目判分完全不同）

学习题目的答案有原文依据，客观题能 100% 程序化判分；
面试**没有标准答案**，只能按维度打分，而且必须做一件学习模块不需要做的事——**简历一致性核对**：

| 维度 | 看什么 |
|---|---|
| `techAccuracy` 技术准确性 | 技术表述是否正确、有没有概念错误 |
| `specificity` 项目具体性 | 有没有讲清自己做了什么、什么数据、什么取舍 |
| `structure` 表达结构 | 有没有条理（背景 → 方案 → 结果） |
| `consistency` **与简历一致性** | 回答是否与简历原文矛盾，矛盾必须扣分并引用简历原话 |
| `relevance` 岗位匹配度 | 是否切题、是否命中岗位核心要求 |

### M6 补充 2：讯飞语音听写接入 + 两个只有真机能抓到的 bug

需求原话：**「我应该怎么找讯飞的api填进去？」** → 顺手把 ASR 这条路彻底打通。

**先说结论：讯飞不是「填一个 Key」就行的。**

| 值 | 长度 | 用途 |
|---|---|---|
| **APPID** | 8 位十六进制 | 请求体 `common.app_id` |
| **APIKey** | 32 位 | HMAC 签名的 `api_key` |
| **APISecret** | 32 位 | HMAC 签名密钥 |

握手签名是 `hmac-sha256(host\ndate\nrequest-line, APISecret)`，再和 APIKey 一起 base64 成
`authorization` —— **只给 APIKey 连签名都算不出来**。

#### 修掉的 3 个断点

| # | 断点 | 现象 |
|---|---|---|
| 1 | **前端表单只渲染一个「API Key」输入框** | 讯飞的另两个值**根本没地方填**；而且厂商下拉里**压根没有「讯飞」**，只能编辑种子数据那条 |
| 2 | **Python ASR 只读 `.env`，从不读 `bb_ai_provider`** | 后端实体、DTO、AES 加密、脱敏全都有，但代码没接 —— 界面上填了也不生效。而且报错文案还写着「请在设置→AI 配置填写」，**是错的** |
| 3 | **`baseUrl` 填了没用** | 代码写死常量，这个字段纯摆设 |

#### 真 bug ①：热词纠错把对的改错了

这是**真机往返测试**才抓到的，之前只拿人造字符串测过纠错，测不出来：

```
期望文本：缓存穿透可以用布隆过滤器解决，缓存击穿用互斥锁重建，缓存雪崩就给过期时间加随机值
原始识别：缓存穿透可以用布隆过滤器解决缓存击穿用互斥锁重建，缓存雪崩就给过期时间加随机值。  ← 讯飞是对的
热词纠错：缓存击穿 → 缓存穿透                                                         ← 改错了！
最终文本：…解决缓存穿透用互斥锁重建…
```

**根因有两层，都得修**：

1. **只看「像不像」，不看「本身是不是已经对了」**。
   `缓存穿透 / 缓存击穿 / 缓存雪崩` 只差一个字，`difflib` 的 ratio 算出来都是 0.75，
   正好卡在阈值上；而「缓存穿透」在候选列表里排前面，于是先被采纳。
   → 加「**先判断这一段是不是本身就是某个热词**」，是就整段跳过，绝不动它。

2. **打平时取了第一个，而不是最像的那个**。
   实测 `缓存激穿`（激/击 同音听错）应该纠成「缓存**击**穿」，
   但 `difflib.SequenceMatcher.ratio()` 对「缓存击穿」和「缓存穿透」**都给 0.75（打平）**。
   → 改用**归一化编辑距离**：前者距离 1（0.75），后者距离 2（0.50），能正确分开。

> 「穿透 / 击穿 / 雪崩」是三个完全不同的概念，**改错比不改更糟** ——
> 这恰好是这套学习材料最核心的一组术语，所以必须修。

#### 真 bug ②：所有厂商都拿 chat 接口做连通性测试

用户点「测试连通」拿到的报错：

```
讯飞语音听写：Illegal character in scheme name at index 2: ws%5Bs%5D://iat.xf-yun.com/v1/chat/completions
```

拆开看：`%5B`/`%5D` 就是 `[` `]`，也就是 `ws[s]://…` ——
**`ws[s]` 是讯飞文档里的简写**（表示 ws 或 wss），用户连方括号一起复制了进去。
而 `/v1/chat/completions` 说明 `test()` **完全没看 capability，一律当 LLM 测**。

四处修：

| 修法 | 说明 |
|---|---|
| **`test()` 按能力分派** | CHAT → 发最小 chat 请求；ASR → 让 Python 做**真实 WebSocket 握手**；EMBED/OCR → 直接读智能体自检结果（这两项是进程内能力，没有独立端点，去探占位 URL 必然失败，会误导用户以为功能坏了） |
| **端点解析容错 `ws[s]`** | `_split_endpoint()` 把 `ws[s]://`、`WS[S]://`、方括号、缺协议前缀统一归一化 |
| **提前拦掉明显的填错** | 对话模型的 Base URL 填成 `ws://` / 含 `ws[s]` 时给中文提示，而不是抛 `Illegal character in scheme name` |
| **讯飞的 Base URL 改成下拉** | 语音听写只有 3 个官方端点，没得选，就不该给自由输入框 |

### M6 补充 3：语音按钮的空格快捷键 + 长按/点按模式

需求原话：**「给说话按钮加上快捷键，在对应的界面长按空格即可说话，可以切换点按模式」**

#### 为什么这个功能比看起来危险

答题页和面试室**都有输入框**，而中文输入法**用空格选候选词**。判定写错的后果是：

- 用户想打一个空格 → 结果开始录音
- 用户在用输入法选词 → 弹出录音并抢走那一次按键

这两种都足够让人直接放弃这个功能。所以判定逻辑做了三层防御 + 一个优先级顺序。

#### 触发规则

| 情况 | 行为 | 原因 |
|---|---|---|
| 焦点在 `textarea` / 文本类 `input` / `select` / `contenteditable` | **完全不接管** | 空格就是「打一个空格」 |
| 输入法组合中（`isComposing` 或 `keyCode === 229`） | 不接管 | 输入法正用空格选词 |
| 焦点在页面空白 / 按钮上 | 接管，并 `preventDefault` | 阻止空格滚动页面、或「点」掉聚焦的按钮 |
| 按住不放的连续 `keydown` | 吞掉但不动手 | 否则会反复触发 start |
| 录音 `disabled` / ASR 不可用 | 吞掉但不动手 | 仍然要防滚动，但不能开始录音 |

**判定的优先级不能调换**：`输入框` 必须排在 `disabled` 之前 ——
否则「输入框 + 组件被禁用」时会把空格吞掉，用户打不出空格。
这一条专门写了测试用例锁住。

**已知取舍**：本组件挂载期间，空格不再能「激活」当前聚焦的按钮
（Tab 之后按回车仍然可以）。在这两个页面上「空格 = 说话」才是用户预期，所以接受。
按钮不算「输入框」，正是为了让「点一下麦克风按钮 → 直接长按空格」这条路径成立。

#### 两种模式

| 模式 | 空格 / 鼠标 | 适合 |
|---|---|---|
| **长按**（默认） | 按住说话，松开即发送 | 短回答，微信那种手感 |
| **点按** | 按一下开始，再按一下结束 | 长回答，不用一直按着 |

按钮右侧的小标签一键切换，选择写进 `localStorage`（`beibei.voice.mode`），两个页面共用。
另外录音中按 **Esc 可直接取消**（丢弃这段，不发请求）。

#### 顺带修掉的两个隐患

| 隐患 | 说明 |
|---|---|
| **快按竞态** | 长按模式下一次很快的点按：权限弹窗还没点完用户就松手了，`stop()` 时 `mediaRecorder` 还是 `null` 什么也没停，等 `getUserMedia` 的 Promise 回来又把 `recording` 置成 `true` —— 按钮永久卡在录音态。加 `wantRecording` 意图标记解决（**这个问题鼠标路径本来就有**） |
| **多实例抢键** | 万一某页放了两个 `VoiceInput`，按一次空格会同时启动两个录音器。用模块级「键盘归属者」保证只有一个响应 |

#### 怎么验证的（这次没靠手点）

把判定逻辑抽成了**纯函数** `beibei-web/src/utils/voiceShortcut.ts`，
配一个不依赖浏览器/服务/凭据的单元测试：

```powershell
node scripts/test_voice_shortcut.mjs
```

**34 条全部通过**，覆盖：6 种输入类元素、两种输入法标志、按钮/空白处的接管、
repeat 吞键、disabled 吞键、非空格键、快捷键关闭、非归属者，
以及上面那条「输入框优先级高于 disabled」的顺序陷阱。

> 抽成纯函数的理由：这是本次风险最高的行为，而它**恰好不需要浏览器就能测**。
> 靠手工在浏览器里点一遍来防回归是不可靠的 —— 尤其是中文输入法那条路径，
> 手点的时候很容易漏掉。

产物侧也做了核对：`VoiceInput` 从 2.73 kB → 5.80 kB，
打包结果里 `isContentEditable`、`isComposing`、`keyCode 229`、`TEXTAREA`、`beibei.voice.mode`
都在，说明没有被 tree-shake 掉。

> ⚠️ **仍未做机器验证的部分**：真实按键流程（按住空格 → 真的录到音 → 松开 → 回填文本）
> 需要浏览器环境，本机没有装 Playwright/Puppeteer，所以没做自动化点击。
> 判定逻辑已 34/34 覆盖，但「按住空格真的能录上音」这一条请手工确认一次。

### M6 补充 4：长录音「语音不可用」—— 一个真 bug + 一次没能证实就否掉的假设

用户反馈：**「我录入了一段语音，发送，结果说语音不可用」**

日志里只有两行，看不出原因：

```
18:03:22 | 音频转码完成：1670400 字节 PCM，约 52.2 秒
POST /api/v1/asr HTTP/1.1" 503 Service Unavailable
```

#### 假设一：讯飞单会话 60 秒上限 —— **做了对照实验，否掉了**

推理看起来成立：讯飞语音听写定位是「1 分钟内的即时语音转文字」，单会话上限 60 秒；
而我们是按 40ms 一帧**实时**上传的，52 秒录音要 52 秒以上才发得完，很容易顶到上限。

于是写了 `scripts/exp_asr_chunking.py` 做 A/B 对照（同一段音频，整段发 vs 切段发）：

```
A. 整段发（不切）  ✅ 成功  耗时 61.2s
B. 切段发          ✅ 成功  耗时 62.2s
```

**整段发 52 秒也成功了** —— 所以这个假设不成立，至少不是那一次的根因。
不能拿一个没证实的理论当结论，所以继续查。

> 切段本身仍然是保留的（见下），因为用户录音上限是 60 秒，
> 整段发会贴着会话上限，属于「迟早会翻车」的设计；但它是保险，不是那次的解药。

#### 真 bug：动态修正的替换下标算错了（长音频必崩）

对照实验里还暴露出一个**更严重、而且必然发生**的问题 ——
106 秒音频返回 200，但文本是这样的：

```
缓存穿透可以用布隆过滤器解决缓缓存缓存击缓存击穿缓存击穿用缓存击穿用护缓存击穿用互斥所…
```

**每一片中间结果都被当成"追加"拼了上去。**

根因：开启动态修正（`dwa=wpgs`）后，讯飞返回的 `rg` 是**结果序号 `sn`**，不是数组下标。
老代码写的是 `pieces[start-1:end] = [text]` —— 按**列表下标**替换。
可 `pieces` 的条目数并不等于 `sn`（只有 text 非空才追加，替换还会改变长度），
所以只要出现过一次 `rpl`，序号就从此错位，之后的替换全部落到错误位置。

修法与讯飞官方 demo 一致：改成**以 sn 为键的字典**
（`pgs=rpl` → 先删 `rg` 范围内的片段再写入；`apd`/缺省 → 直接写入；最后按 sn 升序拼接）。

为什么短音频没暴露：片数少、没触发 `rpl`，恰好蒙对。

#### 真问题：错误信息在中转时被吃掉了

**这条才是「为什么排查这么难」的答案。**

原来的链路是：Python 抛 `AsrUnavailable` → HTTP 503 → Java 的 `AgentClient` 走异常分支
（非 200 拿不到响应体）→ 讯飞的真实错误码（`10114` 会话超时 / `11200` 未授权 / `11201` 额度用完…）
在这一次中转里**丢了** → 前端 `request.ts` 又把 5032 统一显示成
「语音服务暂时不可用，请手动输入」。

三处叠加的结果：用户和开发者都只能看到一句看不出所以然的话，排查全靠猜。修了三处：

| 位置 | 修法 |
|---|---|
| Python `/api/v1/asr` | 失败时返回 **200 + 结构化失败体**（`ok:false / asrUnavailable / permanent / error / hint`），不再用 503 —— 这样错误信息才能穿过 Java |
| `_xfyun_error_hint()` | 补齐**业务错误码**字典（10005/10114/11200/11201/11202/10500…），每个码给一句能直接照做的话；`_xfyun_iat` 的日志也带上 hint |
| `request.ts` | 5032 时优先显示后端 `msg`（`语音识别失败：<真实原因>`），不再用固定文案盖掉 |

另外区分了 `permanent`：凭据没配（True）和网络抖动（False）不是一回事 ——
混在一起的话，一次网络抖动就会让用户以为功能坏了。

#### 顺带加的：失败自动重试

一段 50 秒录音要实时上传 50 秒，中间任何一个瞬时抖动（连接重置、讯飞侧 10500/10700）
都会让整段白录。用户重录一次的代价远高于我们多试两次。
所以 `_transcribe_segment()` 对**非 permanent** 的失败最多重试 3 次（1s、2s 退避）。

#### 实测

```
52 秒录音（精确裁剪到 52.0 秒）走完整链路
  HTTP 200   耗时 60.7s   切 2 段（35s + 17s）
  文本连贯，不再有叠加乱码

短音频回归（scripts/test_asr.py）
  字符级相似度 100.0%   命中关键词 7/7   ✅

错误可诊断性（临时把厂商 enabled 置 0）
  Java 返回 code=5032，msg = 完整可照做的说明，data.permanent = true
  前端会显示「语音识别失败：未配置讯飞凭据。讯飞需要 **三个** 值…」
  （验证完已还原 enabled=1）
```

#### 新增脚本

| 脚本 | 用途 |
|---|---|
| `scripts/repro_asr_long.py <秒数>` | 合成**精确**指定秒数的中文语音并提交，用于复现长录音问题（第一版按字数估时长，估成了 99 秒，后来改成用 ffmpeg 裁剪，才敢说「我测的确实是 52 秒」） |
| `scripts/exp_asr_chunking.py <秒数>` | A/B 对照：整段发 vs 切段发。**就是它把上面那个假设否掉的** |

> ⚠️ **仍然没有定论的部分**：用户那次 503 的确切原因没有复现出来。
> 已修掉的是「必然发生的乱码 bug」「错误信息被吃掉」「瞬时抖动无重试」，
> 并把「长录音贴着会话上限」这个隐患用切段消掉了。如果再出现，日志里现在会有
> 讯飞的确切错误码和对应的处理建议。

### M6 补充 5：用户反馈「录完音解析后什么都不显示」—— 用真机驱动查清楚了

用户反馈：**「我点击说话录完之后，解析后什么都不显示」**

日志里只有请求到达、**返回 200**，没有任何错误：

```
21:14:45 | app.services.asr | 音频转码完成：481920 字节 PCM，约 15.1 秒
INFO: 127.0.0.1:62993 - "POST /api/v1/asr HTTP/1.1" 200 OK
```

#### 第一步：先确认后端返回了什么（结果：后端没问题）

`scripts/diag_asr_response.py` 拿 TTS 语音按**面试室的实际参数**打同一条接口：

```
kbId=19 + 热词纠错 → text = '缓存穿透可以用布隆过滤器解决缓存击穿用互斥锁重建分布式锁要设置过期时间…'（56 字）
                       fixes = [{分布式所 → 分布式锁}]
kbId=19 关热词     → text 56 字
kbId=0  关热词     → text 56 字
```

**三种参数都返回了 56 字** → 后端正常，问题在前端。

#### 第二步：装 puppeteer-core，真的驱动一次浏览器（结果：前端也没问题）

静态看代码看不出毛病，所以不再猜 —— 装 `puppeteer-core` 驱动本机 Chrome
（不下载 Chromium，用已装的），把 `getUserMedia` / `MediaRecorder` 打桩让「点一下」就能产出音频 Blob，
再**拦截 `/api/asr/transcribe`** 返回固定响应 —— 这样测的就是纯粹的「前端拿到文本后有没有显示」。

首次跑（长按模式、成功响应）：**回填成功 ✅**，`textarea` 拿到了文本，提示条显示「识别完成」。

注意用户按钮文案是「点击说话」→ 他处于**点按模式**，于是补测点按模式：也是 **回填成功 ✅**。
两种模式都正常。

#### 第三步：三种后端响应各跑一遍，确认「每种情况用户都该看到点什么」

| 场景 | 输入框 | 提示条 |
|---|---|---|
| 识别成功 | 填入文本 | `识别完成` |
| 识别为空 | 空 | `没有识别到内容，请靠近麦克风重试` |
| 识别失败（5032） | 空 | `语音识别失败：讯飞返回错误 10114：session timeout（单次会话超过 60 秒上限，录音太长，请分段说）` |

**三种情况都有提示。** 所以「什么都不显示」不是这三种里的任何一种 ——
`scripts/test_voice_e2e.mjs` 把这张表固化成了可重跑的测试。

#### 真问题：静态资源没有 Cache-Control，浏览器可能在跑旧包

查响应头时发现的：

```
index.html  →  只有 Last-Modified，**一个 Cache-Control 都没有**
assets/*.js →  同样没有
```

没有 `Cache-Control` 时，浏览器按**启发式缓存**自行决定缓存多久
（经验值是 Last-Modified 起 10% 的时间，这里约 18 分钟）。
后果：前端重新构建、后端重启之后，用户浏览器还在跑旧包，**而且界面上不会有任何提示**。
本次会话前面改了好几轮前端，用户很可能一直看着旧包 —— 这和我之前那次
「讯飞填了没生效」是同一类问题：**改动没到达用户**。

修法（`application.yml`）：

```yaml
spring:
  web:
    resources:
      cache:
        cachecontrol:
          no-cache: true   # 不是「不缓存」，而是每次带 If-Modified-Since 回源问一下
```

`no-cache` 让没变的文件回 304（很便宜），变了的立刻拿到新的。实测已生效：

```
index.html Cache-Control: no-cache
assets     Cache-Control: no-cache
```

之前只记「转码完成」，于是「录完音没反应」时**无从判断是后端没识别出文字、还是前端没渲染**。
现在每次识别结束都记一行摘要：

识别为空时会记 warning，并列出常见原因（麦克风没收到声音 / 录音设备选错 / 录音太短）。

#### 再补一层：录到静音要当场定性，不能只说「没识别到内容」

「讯飞没识别出文字」有两种完全不同的原因：**录到的是静音**（麦克风/权限问题）
还是**讯飞引擎问题**。只看识别结果分不出来，所以加了**音频电平检测**：

```python
rms, peak = _audio_level(pcm)          # int16 量纲
if rms < SILENCE_RMS:                  # 门槛 20
    raise AsrUnavailable("没有拾到声音（RMS=…）…5 条检查清单…")
```

- 正常说话 RMS 一般 500~5000，纯数字静音是 0，设备底噪通常 < 20
- 门槛取 **20**（偏保守）：误判成静音会让用户白折腾麦克风，而真问题可能在别处
- 静音时**直接不发讯飞**，省一次调用，也省 12 秒等待

实测（5 秒纯静音）：

```
code = 5032
msg  = 没有拾到声音（音频电平 RMS=0，几乎为静音）。请依次检查：
       1. Windows「设置 → 系统 → 声音 → 输入」里的设备选对了吗，对着说话看音量条动不动
       2. 麦克风有没有被物理静音，或者笔记本的麦克风静音键
       3. Windows「设置 → 隐私和安全性 → 麦克风」是否允许桌面应用访问
       4. 浏览器地址栏左侧的权限图标里，麦克风是否是「允许」
       5. 如果插着蓝牙耳机，浏览器可能选了耳机麦克风，换成笔记本内置麦克风试试
```

#### 同时上报麦克风设备名

「录到静音」最常见的原因是浏览器**选错了设备**（蓝牙耳机 / Stereo Mix / 虚拟声卡）。
所以前端把实际用的设备名一起传上来，日志里直接能看到：

```
音频电平：RMS=0.0 峰值=0.0（10.0 秒）· 麦克风=Headset Microphone (Bluetooth)
```

前端还会在浏览器控制台打一行 `[语音] 使用麦克风：… 采样率=… 声道=… 自动增益=…`，
浏览器 F12 就能看到，不用去翻后端日志。
